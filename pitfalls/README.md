## 一、`movz` 立即数截断 —— 它伪造了三条假结论

**症状**：写了个辅助函数生成 ARM64 指令，看起来没问题，实际生成了错的机器码。

```python
def movz64(rd, imm16, shift=0):
    return 0xD2800000 | ((shift // 16) << 21) | ((imm16 & 0xFFFF) << 5) | rd
```

看起来很像样对吧。问题是 **`movz` 只能装载 16 位立即数**，`& 0xFFFF` 会把高位直接截掉。

于是：

```python
movz64(1, 131072)      # 0x20000
# 实际生成: movz x1, #0     ← 长度变成 0 了
```

**造成的后果**：binder 的 `mmap` 测试里，`128K`、`1MB`、`1MB-8K` 全部"失败"。
当时得出的结论是"内核只允许 4096 一页的映射"，还写进了报告，自我感觉挺对。

后来修正成 `movz + movk` 链重测：

| mmap 尺寸 | 修正前 | 修正后 |
|---|---|---|
| 4096 | ✅ | ✅ |
| 131072 | ❌ | ✅ |
| 1040384（libbinder 标准值） | ❌ | ✅ |
| 1048576 | ❌ | ✅ |

**binder 的 mmap 从来没被拒绝过。** 之前那整段分析全是垃圾。

**正确写法**：

```python
def load_const(ins, reg, value):
    ins.append(movz64(reg, value & 0xFFFF))
    for sh in (16, 32, 48):
        part = (value >> sh) & 0xFFFF
        if part:
            ins.append(movk64(reg, part, sh))
```

**教训**：

- 手搓机器码时，任何大于 16 位的立即数都要走 `movz+movk` 链
- **生成完必须反汇编核对**，别信辅助函数。用 capstone 把指令列表 dump 出来逐条看，两分钟的事
- 如果某个"内核拒绝"的结论显得很反常（比如"只允许一页映射"），先怀疑自己的工具

## 二、`drain()` 会吃掉 Sahara 的 HELLO

**症状**：为了清掉 USB 缓冲里的"残留数据"，写了个 `drain()`，连接设备后第一件事就调它。

问题是：**Sahara 的 HELLO 包正好 48 字节**，跟"残留数据"长得一模一样。

HELLO 被当成垃圾扔掉之后，后续所有解析全部错位。最诡异的表现是 `END_OF_IMAGE` 的 `status` 字段读出 **1024**——

巧的是 1024 正好等于 `HELLO_RESP` 里 `max_packet_size` 的值（偏移 16 处 `00 04 00 00`）。
这个"巧合"让排查方向完全跑偏，花了很久才想到是数据流错位。

**教训**：

- **协议握手的第一包不能"清理"**，必须先按协议解析
- 要 drain 也得先读第一个包判断类型，别盲清
- 看到"某个字段的值恰好等于另一个已知常量"时，先怀疑字节对齐

## 三、反复折腾会把 EDL 逼进死状态，只能物理断电

**症状**：在 Sahara 上反复试不同方案（改 HELLO_RESP 参数、换 DONE 长度、发 RESET），设备状态一步步崩坏：

```
CM_PROB_NONE           ← 正常
  ↓
CM_PROB_FAILED_START   ← 驱动启动失败
  ↓
USB\VID_0000&PID_0002  ← "未知 USB 设备（设备描述符请求失败）"
```

到了最后一步，软件层面所有手段都救不回来：

| 尝试 | 结果 |
|---|---|
| 重启 USB hub（disable/enable） | ❌ |
| `pnputil /disable-device` + `/enable-device` | ❌ |
| `pnputil /restart-device` | ❌ 而且会把驱动绑定搞丢 |
| 等待自动超时退出 | ❌ 这台机器的 EDL 不会自动退出 |

**唯一有效：长按电源 15 秒强制断电重启。**

中间还遇到过一次"按电源完全没反应"——后来判断是 EDL 待机两小时把电池耗光了（EDL 模式下手机不会自动关机，一直空转等主机）。充了半小时才活过来。

另外记一个实用信息：这台机器上 **音量上 + 电源** 是可靠的强制重启组合（进 Recovery 或直接重启），比单按电源更有效。

**教训**：

- EDL 的 Sahara 状态机很脆，**不要在一个会话里反复试命令**。每次失败宁可物理重启一次，重新来
- 开始前先确认电量（`dumpsys battery` 看 `level`），别在 30% 以下玩 EDL
- 做好"随时需要人手动按电源键"的心理准备

## 四、x64 Windows 拒绝未签名驱动，`DiInstallDevice` 骗不过去

给 `VID_05C6&PID_9008` 绑 WinUSB 驱动，试了一圈：

| 尝试 | 结果 |
|---|---|
| 自写 INF + `pnputil /add-driver`（带 CatalogFile） | ❌ "INF 不含数字签名信息" |
| 自写 INF（去掉 CatalogFile） | ❌ 同上 |
| Windows Update 驱动搜索 | ❌ `HRESULT 0x80248014` |
| `DiInstallDevice` + `INSTALLFLAG_FORCE` 强绑 `winusb.inf` | ⚠️ **状态码变 OK，但没有 `Service` 注册表项，libusb 依然看不见** |
| `SetupDiSetDeviceInstallParams` 限定 `DriverPath` | ❌ 枚举不到驱动（硬件 ID 不匹配） |
| 用已签名的 `android_winusb.inf` 强绑 | ❌ 里面只有 `VID_18D1` 条目 |
| 从 Zadig 里提取内嵌驱动 | ❌ Zadig 是 **UPX 压缩**的，资源目录里没有驱动文件 |

**第四个特别坑**：`DiInstallDevice` 返回成功、设备状态从 `Error` 变 `OK`，看着像搞定了。
但一查注册表：

```
reg query "HKLM\SYSTEM\CurrentControlSet\Enum\USB\VID_05C6&PID_9008\<instance>" /v Service
# ERROR: The system was unable to find the specified registry key or value.
```

**没有 `Service` 项 = 驱动根本没绑上**，只是把错误状态码清掉了。libusb 当然看不见。

**根因**：微软 inbox 的 `winusb.inf` 只匹配这两个 ID：

```
%USB\MS_COMP_WINUSB.DeviceDesc% = WINUSB, USB\MS_COMP_WINUSB
%USB\MS_COMP_ADB.DeviceDesc%    = ADB,    USB\Class_ff&SubClass_42&Prot_01
```

而 EDL 设备的 compatible ID 是 `USB\COMPAT_VID_05C6&Class_FF&SubClass_FF&Prot_10`，两个都不匹配。
自定义 INF 能匹配，但需要签名。

**最终解法：用 [Zadig](https://zadig.akeo.ie/)。**
libwdi 会现场生成针对具体 VID/PID 的 INF，配上它自带的微软交叉签名 `.cat`，所以能装上：

```
Signer Name: USB\VID_05C6&PID_9008 (libwdi autogenerated)
Service:     WinUSB
```

**教训**：

- 判断驱动是否真的绑上，**看注册表的 `Service` 项**，别信设备管理器的状态图标
- Windows 上搞 USB 驱动，Zadig 是最省事的路，别自己造 INF

## 五、pyusb 在 Windows/WinUSB 下会直接瘫痪

**症状**：

```python
d.get_active_configuration()
# NotImplementedError: Operation not supported or unimplemented on this platform

d._ctx.managed_open()
# NotImplementedError: 同上
```

两条路都要读 configuration descriptor，而 WinUSB 后端没实现。拿不到 `device_handle` 的后果：

```python
d.read(0x81, 8)
# KeyError: 129     ← 端点表没建立，pyusb 不认识 0x81
```

**解法：完全绕开 pyusb，用 ctypes 直接调 libusb。**

```python
lib = ctypes.CDLL(libusb_package.find_library('libusb-1.0'))
lib.libusb_bulk_transfer.argtypes = [
    ctypes.c_void_p, ctypes.c_ubyte, ctypes.POINTER(ctypes.c_ubyte),
    ctypes.c_int, ctypes.POINTER(ctypes.c_int), ctypes.c_uint]
```

详见 `tools/edl/rawlibusb.py`。

**顺带一个 API 细节**：`libusb_package.find_library()` **必须传 candidate 参数**：

```python
libusb_package.find_library('libusb-1.0')      # ✅
libusb_package.find_library()                  # ❌ TypeError: missing 1 required positional argument
```

之前把它当 pyusb backend 的回调传进去（`find_library=libusb_package.find_library`）时是 pyusb 内部无参调用它，
所以一直没发现这个签名问题。

## 六、`oplus_sec` 不是解锁校验数据

分区名叫 `oplus_sec`，10 MB，直觉上像是"OPPO 的安全校验分区"，于是花了不少精力琢磨怎么骗过它。

反汇编一看——**是 32 位 ARM ELF（`e_machine=0x28=EM_ARM`），跑在 QSEE 里的 TEE 密码学引擎应用**：

```
OPLUS ROOT CA 1
OPLUS Attestation CA
qsee_stor_write_sectors
qsee_fts_read_file
hal_core_secure_info_verify_sign
Encrypt / Decrypt / Sign / Verify
```

它管签名验签，跟 bootloader 解锁毫无关系。

**教训**：别按分区名猜功能，`file` 一下或者看 ELF 头，十秒钟的事。

## 七、`abl.elf` 是加密的，搜不到字符串不能当证据

一开始在 `abl.elf` 里搜 `fastboot` / `bootloader` / `unlock`，一个都没有，
于是得出"OPPO 压根没编译 fastboot 支持"的结论。

后来算了下熵值：

```
熵 = 7.884 bits/byte
开头 64 字节: 0000000000000000000000000000000078e58c8c3d8a1c4f9935896185c32dd30040030000000000...
```

**代码段是加密的。** 搜不到字符串很正常，代码根本不在明文里。

真正站得住的只有**行为证据**：`adb reboot bootloader` 之后 `ro.boot.bootreason` 明确记录 `bootloader`，
但系统照常启动——说明指令送达了，没有代码去处理它。

**教训**：

- 二进制搜索前先看熵值，高熵（>7.8）说明加密或压缩，字符串搜索无意义
- 静态证据缺失时，**行为证据更可靠**

## 八、`objdump` 不支持 aarch64

MinGW 自带的 `objdump` 查支持列表：

```
supported targets: pe-x86-64 pei-x86-64 elf64-x86-64 ... elf64-little elf32-little
```

只有 x86 系列，没有 aarch64。GNU objdump 的架构支持取决于编译时的 `--enable-targets`。

**改用 capstone**，1.3 MB，国内镜像 5 MB/s 秒装：

```bash
pip install capstone -i https://pypi.tuna.tsinghua.edu.cn/simple
```

```python
import capstone
md = capstone.Cs(capstone.CS_ARCH_ARM64, capstone.CS_MODE_ARM)
for i in md.disasm(code, base_addr):
    print(f'0x{i.address:08x}  {i.mnemonic}  {i.op_str}')
```

## 九、Android 崩溃日志几乎全被关掉

想抓 `dmesg` 看内核崩溃回溯，结果：

| 通道 | 状态 |
|---|---|
| `dmesg` | ❌ `klogctl: Permission denied`（`dmesg_restrict`） |
| `/proc/kmsg`、`/dev/kmsg` | ❌ 权限拒绝（`root:system 620`） |
| `/proc/last_kmsg` | ❌ 节点不存在 |
| `/sys/fs/pstore` | ❌ SELinux 拒（DAC 上 shell 其实在 `log` 组） |
| `/cache/recovery/*` | ❌ SELinux 拒（`cache_file`） |
| `logcat -b kernel` | ❌ 缓冲区存在但**恒为 0 字节**，logd 也读不到 kmsg |

**唯一可用：`adb bugreport`**——dumpstate 在自己的特权域里能读 `/cache/recovery/last_kmsg`，
压缩包里就有（还带 10 个轮转副本，每个 240–490 KB）。

```bash
adb bugreport bugreport.zip
# 里面找 FS/cache/recovery/last_kmsg
```

封装好的脚本见 `tools/crashlog.ps1`。

**教训**：Android 上想看内核日志，别浪费时间试 `dmesg`，直接 `bugreport`。

## 十、PowerShell 的几个坑（顺手记）

写自动化脚本时遇到的，跟安全无关但同样浪费时间：

**1. `$Args` 是保留自动变量**

```powershell
param([string]$Args = "0")     # ❌ 永远拿不到值
```
改名成 `$CallArgs` 就好。

**2. `powershell -File script.ps1 -Param a,b,c` 不会传数组**

整个 `"a,b,c"` 会被当成一个字符串。改用：

```powershell
powershell -Command "& '.\script.ps1' -Param @('a','b','c')"
```

**3. UTF-8 无 BOM 的中文脚本在 PS 5.1 下会解析失败**

PS 5.1 按 ANSI 解码，中文的尾字节可能把后面的引号吞掉，报 `Missing closing '}'`。
**存成 UTF-8 with BOM** 就正常：

```powershell
$c = Get-Content -Raw -Encoding UTF8 $path
[IO.File]::WriteAllText($path, $c, (New-Object Text.UTF8Encoding($true)))
```

**4. 字符串里的 `->` 会被当成重定向**

```powershell
adb shell 'echo "size=28 -> errno=$((256-$?))"'    # ❌ shell 把 -> 当重定向
```

避开 `->`，或者改写。

**5. `$?` 在双引号里会被 PowerShell 抢先解析**

要传给设备就用单引号：`adb shell '...echo EXIT=$?'`。

**6. 泛型语法不能用**

```powershell
[SomeClass]::SizeOf[SomeType]()      # ❌ Unexpected token
[Runtime.InteropServices.Marshal]::SizeOf([type][SomeType])   # ✅
```

## 一句话总结

> **先怀疑工具，再怀疑内核。**

前两条坑加起来浪费的时间，比整趟折腾的其他所有环节都多。
如果不是这两个 bug，kgsl 和 binder 的结论会完全不一样——而且很可能更快就放弃了（因为会早早发现真的打不动）。

写工具的时候多花二十分钟验证，能省掉两天的错误方向。
